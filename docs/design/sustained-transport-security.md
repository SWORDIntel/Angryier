# Sustained transport security boundary

`Transport` frames use HMAC-SHA-256 for integrity/authentication; payloads are **plaintext**, not encrypted. There is no TLS, certificate verification, or built-in cross-host channel. `TcpServer::bind`, `TcpSession::connect`, and `TcpSession::from_stream` reject non-loopback endpoints; an address resolving to both loopback and non-loopback is rejected. Do not bind a public reverse proxy that forwards cleartext to the loopback listener: the public hop must be encrypted and authenticated.

## Cross-host deployment

On each host, bind the Angryier TCP endpoint to `127.0.0.1`/`::1` only. Connect hosts through a separately configured **authenticated and confidential** SSH tunnel or mTLS adapter whose local end terminates on loopback, with an explicit remote host identity and authorization policy. Pin the tunnel endpoint's host/certificate identity and do not permit plaintext fallback. The HMAC key is *additional* application authentication, not a substitute for the encrypted channel. Provision a unique unpredictable 32-byte pairwise secret per coordinator/worker peer pair outside the transport API; do not share keys across pairs or roles. Protect the tunnel, key material, and both host execution environments from untrusted local users; loopback itself does not authenticate a process or provide isolation against a local compromise. Remote command execution and host bootstrap are outside this transport API and must use the same authenticated host identity/authorization boundary; a remote peer's `Status::Completed` is not proof of durable ledger commit.

See the [SSH forwarding example](../guides/distributed-campaigns.md#remote-hosts-tunnel-only-never-plaintext) for the worker listener and coordinator-side `--peer` address. Tunnel authentication identifies the remote host; it does not establish that a worker's result is correct. Only coordinator-verified ledger admission counts as accepted work, not a successful frame MAC or a dispatch notice.

    ## Handshake and reconnect

Every TCP connection must complete the two-sided MAC handshake before it may send or receive a frame. Each side reads a fresh 32-byte OS random challenge (`/dev/urandom` on the Linux appliance; unavailable entropy fails closed), exchanges role-bound proofs, and derives a new per-connection frame MAC key from both challenges. The proof pins ordered sender/recipient peer IDs, `WIRE_VERSION`, contract epoch, and the sealed campaign digest; the latter commits the binary digest, semantic version/profile, script/policy, solver version/policy, and other manifest fields. A mismatched key, role, epoch, build/semantics, or proof fails the connection rather than falling back to legacy frames. Each side also sends its campaign digest **masked** with a key-derived one-time mask (HMAC-SHA-256 over its own nonce), so a peer without the pairwise key learns nothing about the sealed campaign identity, and binds both unmasked digests into the proof: a peer holding the key but running a different manifest is reported as `CampaignMismatch` only after the proof verifies, while a forged or tampered digest, proof, key, role, or epoch stays `InvalidMac`. A failed or partial handshake never installs a session key. Handshake I/O has a 10-second timeout; the caller owns operational read timeouts and connection admission limits thereafter. The exchange authenticates and rekeys but **does not encrypt** traffic, and it does not provide a TLS-style general-purpose identity infrastructure.

The `TcpSession` retains the provisioned pairwise key separately and restores it through `into_transport`; a new connection rekeys even when the caller reconstructs `Transport` with the same pairwise key and zeroed nonce counters. Replay of a frame from an older TCP session fails the new session MAC. Within a session, frame nonces are monotonic and rejects/replays fail closed. A failed write consumes its nonce; never assume a partially delivered frame was committed. An EOF within a handshake or frame is an error. The low-level `Transport::encode`/`feed` codec has **no handshake** and is not a standalone cross-host network API: if a caller sends its frames on another stream with a reused key, that caller must durably persist *both* sent and received nonce high-water marks before acknowledging/sending frames, restore them before reuse, or provision a genuinely fresh key. `set_nonce_high_water` is a restore interface, not persistence; `nonce_high_water` is only a snapshot. Do not interpret these methods as durable replay protection or use raw codec frames to bypass `TcpSession`.
